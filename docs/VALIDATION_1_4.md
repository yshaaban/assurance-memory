# 1.4 validation and longitudinal pilot

Measured on 2026-09-08. The longitudinal comparison was interrupted by an integration defect: the structured-context adapter copied checkout-bound SQLite indexes into new physical workspaces. The index correctly rejected the changed roots. Two second-cycle assignments failed before launching a provider, and their two descendants remained blocked. No replacement trials were run.

The completed provider stages passed their protected checks. This does **not** establish that structured context improves successive maintenance work: only the ordinary-tools arm completed all three cycles. The integration defect, incomplete comparison and preparation costs are part of the result.

## Implementation under validation

Node tooling is 1.4.0, local schema remains 3, and Java modules remain 1.0.0. The [task-start workflow](TASK_WORKFLOW.md) composes the existing scan, investigation, drift and review-archive mechanisms. The [longitudinal runner](LONGITUDINAL_PILOTS.md) adds bounded successive tasks, separate source and note histories, immutable review gates and verified resumption. It adds no detector or authority to approve evidence or close debt.

The study froze the 1.3 compiled investigation implementation at `098d0d6b099b003acdf03247a26a0836f1a612a0`, plus the initial task-start adapter and longitudinal runner, before provider execution. Exact source, runtime, task, oracle and runner digests are retained in the private freeze record. The portability correction and subsequent runner fixes were made after observing the integration failure; they were not substituted into the frozen assignments.

## Study design

Two private, substantial TypeScript projects supplied one mission each. Every mission assigned a real repair, a prospective policy change and an intentional no-change investigation. The mechanisms both concern path policy, so this is a correlated sample, not evidence across unrelated architectural problems. Original project worktrees, including existing uncommitted work, were preserved.

The frozen source inventories contained 812 and 1,711 files, excluding dependency/cache directories. Scans covered configured TypeScript components rather than claiming complete semantic coverage of every repository file. Dependencies were copied from installed trees with recorded provenance, not resolved through a fresh reproducible installation. Neither these snapshots nor the finalization controls establish production capacity.

| Property | Frozen setting |
| --- | --- |
| Assignments | 2 missions × 3 cycles × 2 arms = 12 |
| Comparator | Ordinary repository tools and plain retained notes |
| Treatment | Same capabilities, plus automatically delivered investigation context and optional local CLI |
| Provider | Codex CLI 0.153.4, `gpt-6-astra`, medium reasoning, fresh ephemeral session per stage |
| Schedule | Seed 2026090814; at most two concurrent provider processes |
| Limits | 720 seconds per provider stage; 32,768 UTF-8 bytes per authored handoff |
| Source progression | Only each arm's accepted production changes advance; original checks/configuration remain protected |
| Knowledge progression | Complete accumulated plain notes and declared retained state; histories remain separate |
| Acceptance | Protected checks plus separate AI mechanism review; trace audit records observed reading and reasoning |

Baseline and reference controls were checked before launch. Deliberately harmful controls exercised the requirement boundaries and intentional differences. The evaluator did not repair provider submissions. Later policy tasks were prospective requirements, not claims of observed customer incidents.

Only production changes carry into the next source snapshot. Supplemental tests written by providers remain in sealed patches and separately archived source copies, but are absent from the next candidate workspace. Later notes can therefore cite historical tests that must be rechecked or recreated. This limits conclusions about the usefulness of retained history.

## What the traces establish

The first cycle substantively inspected all ten predeclared owner groups; every primary owner was read before the first production edit. The two running second-cycle agents inspected all eight available owner groups before editing and explicitly reconsidered earlier assumptions. Prior test counts were treated as historical rather than fresh evidence. These observations support careful investigation in the inspected traces, not a causal benefit from the tool.

In the last cycle, one agent supported its decision with valid counterexamples elsewhere but did not substantively read the frozen counterevidence group. Those alternatives are recorded without replacing the predeclared denominator. Both final source inventories independently matched their accepted inputs; production remained unchanged. No unsafe stale reliance was observed in the eight executed traces, within these navigation and checking limits.

Neither structured-context agent invoked the optional local CLI. Context was delivered automatically, but delivery does not prove contribution. One first-cycle brief included the relevant primary file through a different symbol; the other missed the primary owner in its substantive entries. Incidental filenames in coverage warnings are not useful owner retrieval. Both task briefs reported truncation. Query wording and ranking were not tuned after observing these results.

The relevant policy owners had no applicable scanner candidates. Existing structured reviews attach to candidates, so these missions could not test retained review freshness for the reasoning that mattered. Both arms used explicitly unverified handoffs. No artificial candidate was created to fit the study.

The second-cycle mechanism reviews also counted maintenance surface. One accepted policy update changed two production files and introduced six repeated admission predicates. The other changed one production owner, adding one helper and three admission guards. Both met the scoped checks, but correctness alone does not make their future change cost equal. These task-specific counts identify follow-up inspection targets; they are neither comparable complexity scores nor automatic detector findings. Both final cycles added zero production concepts by preserving justified differences.

Separate mechanism reviewers inspected masked packets without provider traces. They were independent of the provider implementations but familiar with the missions; one authored a mission and its oracle. Submitted prose can reveal the treatment. This is partially blinded AI review, not human certification. Trace auditing found no prohibited application-source reads or extra provider launches in the completed audits; instructions and trace review do not provide hermetic read isolation. One second-cycle agent read an allowed generic workflow script whose exact bytes were not frozen; that is a provenance gap.

## Portability correction and regression checks

Provider-free integration controls prepared a fresh index and task packet from each project's accepted first-cycle source at a new physical root. Both passed: approximately 13.703 seconds for one project and 6.303 seconds for the other. These are post-failure controls, not replacement stages or evidence of agent benefit. Both real-project review archives were empty because of the candidate-subject gap.

A separate tiny TypeScript control exercised the complete prepare/review/finalize/restore lifecycle through the real CLI. Its first attempt failed after 1.468 seconds because read-only SQLite export still changed the original index's WAL sidecars. The runner correctly rejected those writes. The exporter was corrected to operate on a disposable snapshot of the closed, quiescent index, preserving the original DB/WAL/SHM bytes. This requires no concurrent index writers and is not an online-backup procedure.

The corrected control completed six deterministic local stages across two arms and three cycles in 5.748 seconds. Nonempty archive history grew from one to one to two records across three physical roots. The original capture stayed stale after import, unchanged rescan and explicit local re-review; only the newly appended local review became current. Source, protected inputs, notes and original index bytes were checked, and all seals verified. Both control attempts remain recorded. They made no model/provider request and do not replace any frozen study assignment. The fixture is tiny; it does not measure finalization overhead on a dependency-heavy project.

Separate scanner-backed integration tests transfer a nonempty review archive between real physical roots. They check unchanged and absent candidates, original captures, persistent staleness, complete re-export, malformed/oversized input rejection before writes, existing-destination refusal and preservation of the original index/archive. Task-start checks also cover exact BOM/line-ending retention, invalid bounds, output exclusivity and symlink invocation on macOS. The adapter checks scan/review revisions while composing the packet; these tests do not establish behavior under every possible concurrent writer interleaving.

The full `npm test` command passed on macOS arm64 with Node 24.16.0 and JDK 21.0.12.1: **124 Node tests, 39 Python tests, and 25 Java scenarios / 85 assertions**. The final Python runner adds twelve tests beyond the frozen study's 27-test suite. They cover repeated finalization/export across three cycles, ordinary dependency symlinks, forbidden source/report/context and captured-runtime edits, unexpected review file/directory quarantine, failure accounting, skipped finalization after provider failure and canonical retained-path validation. Retained ancestor/leaf symlinks and unexpected capture destinations are rejected before they can redirect runner writes or cleanup; external sentinel data survives the regression cases. Export, inventory and total finalization time are recorded separately; no model requests occur in these tests.

These post-study corrections close the missing end-of-task export boundary and reject retained-path aliases before freeze. They do not change the recorded treatment outcomes. No storage or service implementation changed; this revision does not claim a fresh PostgreSQL/restart measurement. Earlier durable-service evidence remains in the [1.3 report](VALIDATION_1_3.md).

## Follow-up gates

1. **Complete the portable task lifecycle.** Export updated reviews at the end of a task, restore into a fresh index at the next checkout, and preserve stale or absent status. Exercise the whole sequence without a provider before freezing another study.
2. **Test useful reasoning without a detector finding.** Investigate a narrow source-subject extension to existing local reviews, retaining capture, dependency invalidation, history and archive semantics. Require a demonstrated workflow before adding a subject type; do not introduce a second memory store.
3. **Improve task relevance before expanding retrieval concepts.** Use separate development and held-out task sets. Measure substantive owner recall, irrelevant content and complete packet bytes against ordinary search; require a falsifiable validation step for every candidate.
4. **Run a fresh paired study across different mechanisms.** These path-policy missions are now development data. Predeclare unrelated tasks, carry useful verification artifacts explicitly, meter reviewer/setup effort, and retain all failures. No replacement requests are hidden inside the current study.
5. **Keep detectors and compiler reuse gated.** Continue the [detector backlog](DETECTOR_BACKLOG.md) with intentional-difference controls and measured policy edit surface. Any compiler reuse must match complete fresh scans and reduce measured end-to-end cost without refreshing stale reviews.

The [design decision](decisions/004-longitudinal-maintenance.md) explains why retained reasoning, independent checking and explicit invalidation are the focus. Tests and source-supported explanations remain scoped evidence; none of these results establishes formal proof or production-scale correctness.
