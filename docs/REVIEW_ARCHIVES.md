# Retained review archives

The workspace SQLite database holds both the current source projection and retained user annotations. Source scans can reconstruct facts and candidates; they cannot reconstruct review text or its captured provenance. A review archive carries every distinct originating annotation record to another index while keeping SQLite as the working store. It does not back up the database's individual restore events.

```sh
assurance-local review-export --db .assurance-cache/index.sqlite --output retained-reviews.json
assurance-local review-import --db recovered/index.sqlite --input retained-reviews.json
```

Use the exported file unchanged. The importer accepts the canonical JSON produced by export, with an optional final newline. Reformatting object fields, inserting duplicate JSON keys, removing records or changing record order causes validation to fail. Existing older indexes need the normal successful scan migration before archive operations; schema 3 prevents older tools from misinterpreting imported history.

## What recovery preserves

Every distinct originating review record is exported, including superseded reviews and notes whose candidate, source file or component has disappeared. Each record carries the original workspace label and review ID, submitted scan number and timestamp, self-reported author, disposition, reason, evidence, candidate capture, source IDs and captures, component contexts, dependency fingerprints and original invalidation. Export reads one consistent SQLite snapshot and includes history beyond the ordinary 200-item query page. Identical originating records appear once even when several local audit rows refer to them; those SQLite rows remain intact.

Import appends retained annotations and permanent `ARCHIVE_RESTORE_REQUIRES_REVIEW` invalidations in one transaction. It preserves the original submitted scan number; the restore invalidation uses the destination scan number, or zero if recovery precedes its first scan. `archive.origin`, `archive.originalInvalidation`, `archive.archiveDigest`, `archive.restoredAt` and `archive.targetSnapshot` distinguish original provenance from the local restore. Snapshot numbers and review IDs in original provenance belong to the original database.

An imported annotation is `STALE` when its original candidate exists and `CANDIDATE_ABSENT` otherwise. Matching source captures do not make it `CURRENT`. A new component name does not remap the original candidate or source IDs. Later scans, component reappearance and source reversion do not clear the invalidation. Inspect the current candidate and submit a new local review with its current `expectedSnapshot` when the retained reasoning remains applicable.

Locally submitted reviews take precedence over restored history for the effective review shown with a candidate and used by ranking. Restoring an older annotation cannot silently displace a destination review. History remains ordered by local insertion ID, so the first item of a history page can be an imported note while the effective review is an earlier local submission. If there is no local submission, the most recently imported record is shown with its stale or absent state. Imported counterevidence never lowers priority.

Identical records are deduplicated by their content digest. Repeating an import does not append another annotation, invalidation or review revision. Importing an unchanged record back into its original store also skips it. Re-export preserves the original record identity without recursively nesting archives. If an original record acquired an invalidation after an earlier export, the changed historical record has a different digest and can be retained alongside the earlier version; both restored versions require re-review. A local invalidation may later become identical to an already imported version. Export then emits that originating record once while preserving both local audit rows and their distinct restore provenance in SQLite. Different authors, captures, original review IDs or invalidations remain distinct records.

## Integrity and limits

Archive version 1 contains an explicit format and annotation-authority label, export timestamp, source workspace/scan/review revision, ordered records and a SHA-256 digest over canonical JSON. Each record has a contiguous sequence number and its own digest; its captured-source fingerprint is checked separately. Import rejects unknown fields, unsupported versions, invalid identities, missing captures or context coverage, duplicate records, malformed values and mismatched checksums before any insert. A failed insert also rolls back the complete import, including its review revision, even when a caller catches the error inside an outer transaction. Concurrent WAL readers keep their prior consistent snapshot until their read transaction ends.

The checksum detects corruption. It does not authenticate an author, verify a source capture or prove where an archive originated. Someone can construct a new checksummed archive with fabricated claims. Every restored record remains a `USER_REPORTED_LOCAL_ANNOTATION`; the supplied author and origin are self-reported. Archive data cannot approve a requirement, establish behavior, resolve debt or create current counterevidence.

An archive must fit within **16 MiB and 10,000 distinct originating records**. Export fails explicitly if that complete record set exceeds either bound; it never emits a truncated success. Both import and export also require JSON depth of at most 32, at most 500,000 values, at most 10,000 members per collection and strings of at most 1,048,576 characters, with tighter bounds for annotation fields. A record retains at most 33 cited sources and the corresponding component contexts. These are format and memory-work bounds, not production-capacity measurements. Archives are materialized and validated in memory; this version provides no streaming or multi-file merge protocol for oversized histories.

For history beyond these limits, or to preserve the source projection, drift, scans and every local review/restore event with its local insertion ID and restore metadata, retain a SQLite-consistent database backup. A review archive contains unique originating annotations and their captures, rather than a full database backup. Copying only a live SQLite main file can omit committed WAL data. The separate assurance service does not automatically retain local annotations. Archives contain review text, paths and metadata from the original workspace and should be handled with the same access controls as that database.
